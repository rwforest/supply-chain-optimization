# MPS cuOpt Pipeline — FJSP / CVRPTW / MEIO

[← Back to README](../README.md) · Related: [Optimization Objectives](optimization-objectives.md) · [Disruption Scenarios](disruption-scenarios.md) · [Multi-Period & Decomposition](multi-period-and-decomposition.md)

Notebook `09_mps_cuopt_pipeline` takes the accelerator in a different direction from the TTR/TTS LP stress tests. Instead of re-solving one network-wide linear program per disruption, it derives **three distinct operations-research problems** from the MPS-like network and solves each with the right tool: two on **NVIDIA cuOpt's GPU solvers**, one on the existing **Pyomo/HiGHS CPU** stack. It follows the design doc [`MPS Supply Chain Optimization Pipeline.md`](../MPS%20Supply%20Chain%20Optimization%20Pipeline.md).

| Scenario | Problem | Model type | Solver | Compute |
|---|---|---|---|---|
| **II — FJSP** | Flexible Job-Shop Scheduling of back-end assembly/test | Sequence-based MILP (makespan min) | cuOpt in-process `Problem` (Feasibility Pump / PDLP) | **GPU** |
| **III — CVRPTW** | Capacitated Vehicle Routing with Time Windows | Routing (`cuopt.routing.DataModel`) | cuOpt GES metaheuristic | **GPU** |
| **I — MEIO** | Multi-Echelon Inventory Optimization (Guaranteed Service Model) | Piecewise-linearized LP/MILP | Pyomo + HiGHS | **CPU** |

Everything is **additive**: nothing in `scripts/utils.py`, `disruption_scenarios.py`, `realistic_topologies.py` (beyond widening one type hint to accept `"mps"`), or the `01`–`08` notebook chain changes. The MPS network is generated by `generate_complex_network("mps")` (complex, ~2,300 nodes) or `generate_complex_network_at_scale("mps", scale="planet")` (~76,000 nodes) exactly like the Nvidia/Apple anchors — notebook `09`'s `scale` widget switches between them. See [Planet scale](#planet-scale) below for how each model stays tractable at 76k nodes.

## ⚠️ Support caveat (read first)

Running **NVIDIA cuOpt on Databricks serverless GPU compute is technically feasible but is NOT officially supported or documented by Databricks or NVIDIA** as of this writing. Concretely:

- The cuOpt / cuDF wheels install from **NVIDIA's own package index** (`https://pypi.nvidia.com`) via `requirements-gpu.txt`, not from the Databricks runtime image.
- The GPU sections of `09` are gated behind a **`run_gpu` widget (default `"no"`)**. With `run_gpu="no"`, the notebook runs the derivation layer and the CPU MEIO solve end-to-end on any cluster — the cuOpt install and GPU solves are skipped entirely. `requirements.txt` (installed by every other notebook) never pulls cuOpt.
- Databricks serverless GPU (AI Runtime) is itself **Public Preview**: single-node only, 7-day max runtime, limited AWS regions. cuOpt additionally requires NVIDIA Volta+ (compute capability ≥ 7.0), CUDA 12.0+, Python 3.11–3.14, OpenSSL 3, Linux/WSL2.

Treat the GPU path as an integration experiment. The CPU-verifiable parts (derivation + MEIO) are covered by `tests/test_mps_cuopt.py` and run in CI without a GPU; the GPU solve tests use `pytest.importorskip` so they **skip** rather than fail when the wheels aren't present.

## The derivation layer — `scripts/mps_derivation.py`

The core design decision (per the plan) is that FJSP/CVRPTW/MEIO are **derived from the generated network**, not invented as standalone toy instances. `mps_derivation.py` is the single translation layer. It imports **no** `cuopt`/`cudf`/`pyomo` — every function takes and returns plain dicts/lists, so it is fully unit-testable without a GPU or a solver.

| Function | Derives | From |
|---|---|---|
| `select_backend_machines(dataset)` | FJSP machines (Chengdu test cells + OSAT packaging lines), each split into parallel sub-machines sized by node capacity `c` | tier-2 anchors tagged `wafer_sort_final_test` / `advanced_packaging_osat` |
| `derive_fjsp_jobs(dataset, machines)` | Production lots, each a 4-op sequence (die attach → wire bond → encapsulation → electrical test) | tier-1 demand `d`, capped at `max_jobs` for a tractable demo |
| `derive_fjsp_processing_times(...)` | Per-`(job, op, machine)` processing times | facility `production_delay` from `calibrate_cost_fields`, jittered per op/job |
| `select_cvrptw_depots(dataset)` | Distribution depots | Chengdu + Penang tier-2 anchors |
| `derive_cvrptw_customers(dataset)` | One customer per product line (region + demand) | tier-1 nodes |
| `derive_cvrptw_time_windows(...)` | Delivery windows (tighter for fragile supply) | dominant supplier `criticality` feeding each tier-1 line |
| `derive_cvrptw_distance_time_matrix(...)` | Square cost/time matrix (depot at index 0) | coarse inter-region travel-minute lookup (no real geocoding) |
| `derive_meio_network(dataset)` | GSM network: nodes, edges, holding cost, lead time, demand mean/std, service-level `z` | full tier1∪tier2∪tier3 graph + calibrated fields + criticality |

`electrical_test` is restricted to test-capable (Chengdu) machines, mirroring MPS owning its own final-test step.

## Scenario II — FJSP (`scripts/fjsp_cuopt.py`)

A sequence-based MILP minimizing **makespan** `Cmax`:

- **Variables:** `Cmax` (continuous); `s[j,o]`, `c[j,o]` (start/completion, continuous); `x[j,o,m]` (binary machine assignment); `y[j1,o1,j2,o2,m]` (binary sequencing on a shared machine).
- **Constraints:** exactly-one-machine assignment; completion = start + processing time; job precedence; makespan ≥ every job's last completion; Big-M disjunctive pairs so a machine runs one op at a time.

Two layers keep it GPU-free-testable:

1. **`_fjsp_milp_spec(jobs, machines, processing_times)`** — pure Python, returns the full MILP as data (variable list + kinds/bounds, objective coefficients, constraint rows as sparse `{var: coef}` + sense + rhs, Big-M). Imports nothing from cuOpt, so its variable/constraint counts and shapes are unit-testable anywhere.
2. **`build_fjsp_problem(...)`** wraps that spec into a cuOpt in-process `Problem` (`from cuopt.linear_programming.problem import Problem` — no server required). `solve_fjsp(problem)` runs the GPU solve; `decode_fjsp_result(...)` turns raw variable values into a per-machine schedule. `_raw_var_values` is deliberately defensive about cuOpt's solution-accessor API, which has shifted across releases.

---

## Scenario III — CVRPTW (`scripts/cvrptw_cuopt.py`)

Same two-layer split:

1. **`_cvrptw_datamodel_spec(...)`** — pure Python, returns the routing model as data (location count, square cost/time matrices, per-order demand, time windows, per-vehicle capacities, depot index). Its `.validate()` method raises on any matrix/vector shape inconsistency — the same checks a cuOpt `DataModel` would otherwise fail on only at solve time.
2. **`build_cvrptw_datamodel(...)`** wraps it into a `cuopt.routing.DataModel` (needs `cudf` for the matrices). `solve_cvrptw(...)` runs the GES metaheuristic on GPU; `decode_cvrptw_result(...)` extracts per-vehicle routes.

v1 uses a single homogeneous depot (the first in the list) and a fixed per-stop service time; multi-depot and heterogeneous fleets are documented extensions.

## Scenario I — MEIO (`scripts/meio_pyomo.py`, CPU)

MEIO stays **CPU-only by design**. The Guaranteed Service Model minimizes total safety-stock capital:

```
minimize  Σ_i  h_i · z_i · σ_i · sqrt(NLT_i)
```

where `h` = unit holding cost, `z` = service-level safety factor, `σ` = demand std, and `NLT_i` = net lead time at node `i` = inbound service time + processing lead time − outbound service time. The `sqrt` makes the exact objective **nonlinear**, which the repo's HiGHS (LP/MILP-only) solver can't handle natively.

### Why piecewise-linear (and why not the obvious LP relaxation)

Minimizing `c·sqrt(NLT)` with `c > 0` is minimizing a **concave** function — a genuinely non-convex problem. Two tempting-but-wrong shortcuts:

- A plain **convex-combination (lambda) LP relaxation** lets a minimizing solver put weight on the two *extreme* breakpoints (the global chord), which lies far *below* a concave curve → massive under-estimate (measured ~95% error on the MPS network).
- Pure **tangent-line cuts** over-constrain the other way (the upper envelope) and blow up.

The correct fix is the **SOS2 / incremental piecewise-linear** form, which forces the approximation onto the true piecewise-linear interpolant of `sqrt` (at most two *adjacent* breakpoints active). `build_meio_model` uses Pyomo's `Piecewise` with `pw_repn="INC"` — the incremental representation, which enforces the same adjacency using ordinary binary variables + linear constraints and therefore works through **HiGHS's MILP interface** (HiGHS's Pyomo persistent solver does *not* support native SOS constraints). Breakpoints span `[0, nlt_ub]`, where `nlt_ub` is the **DAG longest-path lead time** (a tight per-node net-lead-time bound), keeping the breakpoints dense over the range each node can actually occupy.

On the generated MPS network this lands within **~1%** of the exact true-sqrt objective — `solve_meio` reports the approximation cost and `true_safety_stock_cost(...)` recomputes the exact value so the notebook and `tests/test_mps_cuopt.py` can bound the gap.

### `mode="nonlinear"` — a documented stub

`build_meio_model(network, mode="nonlinear")` raises `NotImplementedError`: the exact nonlinear (MINLP) solve would need an Ipopt-class solver (e.g. `cyipopt`), a platform-sensitive dependency most users won't want, so it's an opt-in future `nlp` extras group rather than a default. `mode="piecewise_linear"` is the default and the only path built out in v1.

## Planet scale

The MPS anchor supports the same `"planet"` preset as Nvidia/Apple (`generate_complex_network_at_scale("mps", scale="planet")`, ~76,000 nodes). Notebook `09`'s `scale` widget (`"complex"` / `"planet"`) switches which dataset it loads. Each of the three models is made scale-compatible in a way that fits what it actually represents:

- **FJSP — scale-invariant by construction.** The scheduling problem is MPS's *own* back-end (the wholly-owned Chengdu wafer-sort/final-test facility plus its named OSAT partners), not the entire synthetic packaging market. So `select_backend_machines` (and `select_cvrptw_depots`) key off the **real named anchor set** `_MPS_TIER2_ANCHOR_NAMES` (from `company_profiles`), not "any node with a `company_name`" — because the synthetic "rest of market" peers *also* carry fictional company names and at `scale_factor=25` would otherwise inflate the machine list from ~11 to ~600, exploding the MILP (the pairwise disjunctive term is `O(ops² × shared_machines)`). Result: **11 machines / 2 depots at any scale**, so the FJSP MILP is identical between complex and planet.
- **CVRPTW — naturally scale-invariant.** Depots are the 2 real hubs and there's one customer per product line (6), independent of node count.
- **MEIO — subsampled.** MEIO does span the whole network, and the full 76k-node GSM MILP has one INC-piecewise block per node → hundreds of thousands of binaries; measured HiGHS solve time is **~23 minutes** (optimal, 0.56% approximation error, 4.8 GB RSS). `derive_meio_network(dataset, max_nodes=..., sample_fraction=..., seed=...)` subsamples first — **always keeping** every tier-1 node, every real named anchor, and every `monopoly_bottleneck`/`oligopoly` node (the fragile, capital-intensive nodes where safety-stock placement matters), and randomly sampling the commodity long tail, mirroring the `sample_fraction`/`always_include_criticality` pattern in `disruption_scenarios.single_supplier_failure_scenarios`. Demand is propagated over the *full* network first so kept nodes retain accurate demand; edges are then restricted to the kept set. A ~2,500-node sample solves in **~7 s**, optimal, within **~0.6%** of the exact-sqrt objective. Defaults (`max_nodes=None`, `sample_fraction=1.0`) reproduce today's full-network behavior exactly, so complex scale is unchanged. Notebook `09` passes `max_nodes=2500` only when `scale="planet"`.

## Non-goals (v1)

The design doc's §8 describes a 5-stage **agentic pipeline**: Adexa digital-twin ingestion → NVIDIA NIM/LLM reasoning → LangChain sub-agents that formulate the constraint matrices → cuOpt GPU solve → Adexa S&OE execution. Notebook `09` computes the FJSP/CVRPTW/MEIO results **directly** and does **not** build that orchestration layer. Wiring these three model runs behind this repo's existing `Supply_Chain_Supervisor` MAS / Genie / MCP infrastructure (so a natural-language planner query routes to the right solve) is a natural future extension, not part of v1.

## Testing

`tests/test_mps_cuopt.py` covers:

- **Derivation** — machine groups, job/op eligibility, electrical-test restriction, depot selection (Chengdu + Penang), customer/window consistency, distance-matrix squareness, MEIO node-set equality with the source dataset.
- **Model specs** — FJSP MILP variable/constraint counts and that every constraint references only declared variables; CVRPTW spec shape validation (including that `.validate()` rejects a corrupted matrix).
- **MEIO** — optimal solve on the MPS network, the piecewise-linear approximation error bounded < 5% vs. true-sqrt, breakpoint coverage, and that `mode="nonlinear"` is a documented stub.
- **Planet scale** — FJSP machines / CVRPTW depots are scale-invariant (complex vs planet), MEIO's default keeps the full network while `max_nodes` subsampling stays bounded, always keeps tier-1 + anchors + monopoly/oligopoly nodes, restricts edges to the kept set, is deterministic per seed, and the sampled planet-scale MEIO still solves optimally within 5% of true-sqrt.
- **GPU solves** — `build_fjsp_problem`/`solve_fjsp` and `build_cvrptw_datamodel`/`solve_cvrptw` guarded with `pytest.importorskip("cuopt")` / `("cudf")` so they **skip** (not fail) without the GPU wheels.

The MPS dataset also rides the existing `tests/test_realistic_scenarios.py::GENERATORS` parametrization, so it inherits all the schema/index/parameter-validity and bounded-scenario-solvability checks the Nvidia/Apple anchors get.

Run from the repo root:

```bash
python -m pytest tests/ -v   # MPS + derivation + MEIO pass; GPU tests skip without cuOpt
```
